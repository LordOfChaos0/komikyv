Спецификация требований к программному обеспечению (SRS)
Приложение к заданию на практику по веб-технологиям

Минимальный уровень — обязательная база, без которой работа не принимается (оценка 3).
Рекомендуемый уровень — критерии для оценок «хорошо» (4) и «отлично» (5).
Все пункты должны быть подтверждены скриншотами или ссылками в итоговом отчёте.


1. Функциональные требования (бизнес-логика)

| №   | Требование                     | Минимальный уровень (MIN)                                                                 | Рекомендуемый уровень (REC)                                                                 |
|-----|--------------------------------|-------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| 1.1 | Аутентификация и регистрация   | Реализована форма регистрации (Email/логин + пароль) и входа. Пароль хэшируется и не хранится в открытом виде. | Вход через внешние сервисы (OAuth 2.0: ВКонтакте / MAX / SberID и др.). Реализовано восстановление пароля через Email. |
| 1.2 | Ролевая модель (RBAC)          | Присутствуют минимум 2 роли: авторизованный пользователь и администратор. Доступ к страницам ограничен в зависимости от роли. | Присутствуют 3+ роли (например: гость, пользователь, модератор, администратор, менеджер). Настроены гибкие права доступа (CRUD для разных сущностей). |
| 1.3 | Базовые CRUD-операции          | Реализованы операции Create, Read, Update, Delete для главной бизнес-сущности (товар, заказ, проект, объявление и т. д.). | CRUD реализован для всех основных сущностей системы (пользователи, категории, заказы, отзывы). Реализовано мягкое удаление (soft delete): запись в БД помечается как удалённая, но не исчезает. |
| 1.4 | Поиск и фильтрация             | Реализован поиск по одному текстовому полю (например, по названию).                        | Реализована полнотекстовая фильтрация по 3+ критериям (категория, цена, дата, статус) с возможностью сортировки (по дате / цене / популярности). Использована пагинация (не более 10–20 записей на страницу). |
| 1.5 | Бизнес-процессы (сценарии)     | Автоматизированы 3 бизнес-процесса из описанных в Activity Diagram.                       | Автоматизированы все 4+ описанных бизнес-процесса. Реализована машина состояний (статусы: «Новый» → «В работе» → «Завершён», с ограничением переходов). |


2. Требования к базе данных (БД)

| №   | Требование                     | Минимальный уровень (MIN)                                                                 | Рекомендуемый уровень (REC)                                                                 |
|-----|--------------------------------|-------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| 2.1 | Количество таблиц (сущностей)  | База данных содержит не менее 4 связанных таблиц (например: Users, Roles, Products, Orders). | База данных содержит не менее 8–10 таблиц, отражающих всю предметную область (включая справочники, связи многие-ко-многим, логирование). |
| 2.2 | Связи между таблицами          | Использованы связи 1:N (один ко многим). Внешние ключи (FK) явно прописаны в схеме.        | Использованы связи 1:N и M:N (многие ко многим) с промежуточными таблицами. Настроены каскадные обновления / удаления (ON DELETE CASCADE / SET NULL). |
| 2.3 | Индексы и производительность   | Не требуется.                                                                              | Созданы индексы для полей, по которым чаще всего выполняется поиск и фильтрация (email, status, created_at, внешние ключи). Приложен скриншот плана выполнения запроса (EXPLAIN). |
| 2.4 | Типы данных и нормализация     | Данные хранятся в нормализованном виде (соответствие 2-й нормальной форме: неделимые значения). | Данные нормализованы до 3-й нормальной формы (отсутствие транзитивных зависимостей). Использованы расширенные типы (JSON/JSONB для хранения гибких атрибутов, ENUM для статусов). |


3. Требования к пользовательскому интерфейсу (UI/UX)

| №   | Требование                     | Минимальный уровень (MIN)                                                                 | Рекомендуемый уровень (REC)                                                                 |
|-----|--------------------------------|-------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| 3.1 | Адаптивность (Mobile First)    | Страницы корректно отображаются в браузере на десктопе (разрешение от 1024px).             | Приложение адаптивно и корректно работает на трёх типах устройств: десктоп, планшет (768px) и смартфон (320px). Элементы интерфейса не «разваливаются». |
| 3.2 | Навигация                      | Присутствует главное меню с переходом между основными разделами (Главная, Каталог/Список, Личный кабинет). | Присутствуют «хлебные крошки» (breadcrumbs) или сайдбар. Навигация интуитивно понятна (юзабилити-тест на 1 пользователе пройден). |
| 3.3 | Валидация форм                 | Валидация реализована на серверной стороне (защита от некорректных данных).                | Реализована двусторонняя валидация: клиентская (мгновенная подсветка ошибок без перезагрузки) и серверная (дублирующая защита). Поля подсвечиваются красным, выводятся понятные подсказки. |
| 3.4 | Обратная связь для пользователя | После выполнения действия (успех/ошибка) появляется текстовое сообщение на странице.       | Используются модальные окна или всплывающие Toast-уведомления (например, «Заказ успешно создан»), которые автоматически исчезают через 5 секунд. |
| 3.5 | Качество вёрстки               | Использован CSS-фреймворк (Bootstrap 5, Tailwind) или собственные стили. Минимальный визуальный стиль единообразен. | Использована кастомная стилизация (собственная дизайн-система). Приложение выглядит как современный веб-сервис (продуманы тени, анимации переходов, иконки). |


4. Требования к административной панели (CMS / Admin)

| №   | Требование                     | Минимальный уровень (MIN)                                                                 | Рекомендуемый уровень (REC)                                                                 |
|-----|--------------------------------|-------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| 4.1 | Доступ к панели                | Существует отдельная точка входа (URL) для администратора.                                 | Доступ к панели защищён 2FA (двухфакторная аутентификация) или вход только по специальному токену (опционально). |
| 4.2 | Управление пользователями      | В админ-панели можно просматривать список всех пользователей и блокировать / удалять их.  | Можно не только блокировать, но и редактировать данные пользователей, назначать им роли, а также сбрасывать пароль вручную. |
| 4.3 | Управление контентом           | Администратор может добавлять / редактировать / удалять записи главной сущности (чтобы не лезть в БД напрямую). | Реализован CRUD для всех сущностей системы прямо из интерфейса. Также есть быстрые действия (опубликовать / снять с публикации). |
| 4.4 | Статистика / Дашборд           | Не требуется.                                                                              | На главной админ-панели присутствуют графики (например, количество регистраций по дням, количество заказов) и счётчики (всего пользователей, заказов за месяц). Данные меняются в реальном времени. |


5. Нефункциональные требования (инфраструктура, безопасность, документация)

| №   | Требование                     | Минимальный уровень (MIN)                                                                 | Рекомендуемый уровень (REC)                                                                 |
|-----|--------------------------------|-------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| 5.1 | Безопасность                   | Все пароли хэшированы (bcrypt или аналоги). Настроена защита от SQL-инъекций (через ORM или параметризованные запросы). | Внедрён CSRF-токен для форм. Заголовки безопасности настроены корректно (CORS). Логирование всех попыток взлома (авторизации). |
| 5.2 | Размещение (деплой)            | Приложение доступно по публичной ссылке в интернете (хостинг, VPS, облачная платформа). Локальная сборка не принимается. | Настроен SSL-сертификат (протокол HTTPS). Настроен автоматический деплой при пуше в главную ветку репозитория (CI/CD). |
| 5.3 | Система контроля версий        | Код загружен в репозиторий (GitHub/GitLab).                                               | В репозитории более 10 коммитов с осмысленными сообщениями (не fix, а «добавлена валидация формы заказа»). Ветки main и develop. |
| 5.4 | Документирование API (бэкенд)  | Не требуется.                                                                              | API задокументировано через Swagger / OpenAPI (доступно по ссылке /api-docs).               |
| 5.5 | Обработка ошибок (HTTP 404, 500) | При переходе на несуществующую страницу пользователь видит стандартную страницу ошибки.  | Настроены кастомные страницы ошибок (404 — «Страница не найдена» с поиском; 500 — «Технические работы» с предложением связаться с поддержкой). |


6. Итоговый чек-лист для студента

Перед сдачей проекта необходимо ответить «Да» на все пункты минимального уровня. Если требуется получить высокий балл, рекомендуется выполнить 60%+ пунктов из столбца «Рекомендуемый уровень».
