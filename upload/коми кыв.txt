Тема практики:
Разработка интерактивной веб-платформы «Коми кыв» для изучения коми языка с интеграцией нейросетевых моделей синтеза речи и диалоговых тренажеров.
Описание:
Система предназначена для сохранения и популяризации коми языка через современные образовательные технологии. Она решает проблему отсутствия интерактивных учебных материалов и живых носителей языка для практики, предоставляя пользователям возможность тренировать произношение и вести диалоги с искусственным интеллектом. Платформа помогает как новичкам, так и продолжающим изучать язык, делая процесс обучения увлекательным за счет элементов геймификации и адаптивной подачи материала.
Пользователи:
	Ученик (Студент/Пользователь) – проходит интерактивные уроки, общается с диалоговым тренажером, тренирует произношение через системы распознавания и синтеза речи, получает достижения и отслеживает свой прогресс в рейтинге.
	Преподаватель (Методист) – создает и редактирует учебные модули, добавляет новые диалоговые сценарии и словарь для нейросети, отслеживает успеваемость учеников и формирует отчеты по прогрессу.
	Администратор системы – управляет правами доступа, мониторит нагрузку на серверы и работу нейросетевых моделей, настраивает параметры геймификации, а также решает технические проблемы и обновляет базы данных.
Архитектура: 
Клиент-серверную архитектуру с элементами микросервисного подхода.
Законы и нормативные документы:
	152-ФЗ «О персональных данных» - Согласие на обработку данных, шифрование голосовых слепков, удаление аккаунта.
	ГК РФ (авторское право) – Указываем авторов учебных текстов, проверяем лицензии на аудио с носителями.
	149-ФЗ – Защищаем переписку с ботом, фильтруем запрещенный контент.
	Закон «Об образовании в РФ» - РФ» - Указываем, что сервис не выдаёт дипломы гос. образца без лицензии.
Бизнес-процессы
	Прохождение интерактивного урока.
	Тренировка диалога с нейросетью.
	Анализ и оценка произношения.
	Добавление нового учебного модуля.
	Начисление достижений и очков.

2 Назначения и цели создания системы
2.1 Вид автоматизируемой деятельности
Система автоматизирует образовательный процесс изучения коми языка, включая теоретическое обучение, тренировку аудирования, практику произношения с использованием ASR-моделей и ведение свободных диалогов с NLP-агентом. Также автоматизируется методическая работа преподавателей по созданию и модерации учебных модулей.
2.2 Цели создания системы и показатели назначения
1.	Повышение вовлеченности: Внедрение геймификации и адаптивного обучения для удержания внимания учеников.
2.	Автоматизация проверки: Снижение нагрузки на преподавателей за счет автоматической проверки произношения и грамматики нейросетями.
3.	Масштабируемость контента: Предоставление преподавателям конструктора модулей с автоматической генерацией аудио (TTS) для новых слов.
4.	Сохранение языка: Создание цифрового репозитория диалоговых сценариев и словарного запаса.
 
3 Характеристика объектов автоматизации
Объектом автоматизации является процесс обучения коми языку и управления учебным контентом. 
Субъекты процесса:
1.	Ученик: изучает теорию, проходит тесты, записывает голосовые ответы, взаимодействует с ИИ-собеседником.
2.	Преподаватель: формирует структуру модулей, добавляет словари, настраивает параметры прохождения и диалоговые сценарии.
3.	Администратор: модерирует пользовательский и преподавательский контент, управляет ролями и настройками системы.
4.	Нейросетевые модели (Внешние/Локальные сервисы): выполняют синтез речи (TTS), распознавание голоса ученика (ASR) и генерацию ответов в диалогах (NLP).
 
4 Требования к системе
4.1 Требования к системе в целом
4.1.1 Требования к структуре и функционированию
Система должна иметь клиент-серверную архитектуру с выделением микросервисов для обработки ресурсоемких задач (ML-модели).
1.	Frontend (Клиент): SPA-приложение, работающее в современных браузерах.
2.	Backend (Основной сервер): REST API для управления пользователями, прогрессом и контентом.
3.	ML-Сервисы: Отдельные контейнеры для TTS, ASR и NLP, взаимодействующие с основным Backend через очереди сообщений (для асинхронной обработки) или gRPC/API.

4.1.5 Требования к безопасности
1.	Защита данных: Хэширование паролей (bcrypt/Argon2).
2.	152-ФЗ: Голосовые слепки учеников (аудиофайлы) считаются биометрическими данными. Они должны храниться в зашифрованном виде или автоматически удаляться после проверки ASR-моделью (если не используются для дообучения).
3.	Ролевая модель: Ученик, Преподаватель, Администратор. Доступ к API защищен JWT-токенами.
4.	Модерация: Любой новый модуль, созданный преподавателем, должен проходить автоматическую проверку и ручную модерацию администратором перед публикацией.
4.2 Требования к функциям, выполняемым системой
4.2.1 Состав и содержание функций
Система реализует следующие укрупненные функции:
1.	Управление профилем и прогрессом ученика (геймификация).
2.	Прохождение интерактивных уроков (текст, тесты, аудио).
3.	Тренировка диалогов с ИИ (ASR + NLP + TTS).
4.	Конструктор учебных модулей (для преподавателей).
5.	Модерация и публикация контента (для администраторов).
4.2.2 Требования к бизнес-процессам
Реализация бизнес-процессов должна строго соответовать разработанным диаграммам действий.
1.	Бизнес-процесс «Прохождение интерактивного урока»:
Ученик выбирает урок, система загружает материалы и генерирует аудио через TTS. Ученик выполняет упражнения (перевод, сопоставление, аудио-распознавание). Система проверяет ответы в реальном времени, начисляет баллы, предоставляет подсказки при ошибках. По итогу обновляется прогресс и начисляются достижения. 
 
Рисунок 4.5 – Диаграмма действий бизнес-процесса «Прохождение интерактивного урока» 
2.	Бизнес-процесс «Тренировка диалога с нейросетью»:
Ученик выбирает сценарий. Система инициирует диалог, произнося первую реплику (TTS). Ученик отвечает голосом или текстом. При голосовом вводе ASR преобразует речь в текст и оценивает произношение. NLP-модель анализирует грамматику и контекст, генерирует ответ. Процесс цикличен. По итогу формируется детальный отчет с разбором ошибок.
 
Рисунок 4.6 – Диаграмма действий бизнес-процесса «Тренировка диалога с нейросетью»
3.	Бизнес-процесс «Добавление нового учебного модуля»:
Преподаватель создает модуль, наполняет его теорией, словарем и упражнениями. Система автоматически проверяет контент, генерирует аудио через TTS для новых слов и проверяет орфографию. После сохранения черновика и исправления ошибок модуль отправляется на модерацию Администратору. После одобрения модуль публикуется.

4.2.3 Требования к интеграции и внешним взаимодействиям
Система должна интегрироваться с внешними или локально развернутыми API:
1.	TTS (Text-to-Speech): Для озвучки словаря и реплик ИИ на коми языке.
2.	ASR (Speech-to-Text): Для транскрибации ответов ученика и оценки точности произношения.
3.	NLP (LLM): Для генерации контекстных ответов в диалоговом тренажере с учетом грамматики коми языка.

	Темы диалога (знакомство, покупки, путешествия и т.д.)
	Уровня сложности
	Примерного времени прохождения
	Прогресса выполнения

	Структуру диалога
	Возможные реплики
	Ключевые фразы и vocabulary
	Критерии оценки

7.	Ученик может:
	Повторить прослушивание реплики
	Попросить перевести реплику на русский
	Попросить замедлить речь
8.	Ученик произносит ответ вслух (голосовой ввод) или вводит текст (текстовый ввод).
9.	При голосовом вводе:
	Система записывает аудио ответ ученика
	Модель распознавания речи (ASR) преобразует аудио в текст
	Система анализирует качество произношения
10.	Диалоговая нейросеть анализирует ответ ученика:
	Грамматическую правильность
	Лексическую уместность
	Соответствие контексту диалога
	Полноту ответа
11.	Система формирует ответ нейросети на реплику ученика на коми языке.
12.	Система воспроизводит ответ нейросети с использованием синтеза речи.
13.	Процесс продолжается до завершения сценария диалога.
14.	По окончании диалога система формирует детальный отчет:
	Общая оценка диалога
	Оценка произношения (если был голосовой ввод)
	Оценка грамматики
	Оценка словарного запаса
	Список ошибок с пояснениями
	Рекомендации для улучшения

4.1. Общее описание бизнес-процесса
Бизнес-процесс «Добавление нового учебного модуля» описывает работу преподавателя по созданию и публикации нового учебного контента.
Участники процесса:
	Преподаватель (Методист)
	Система (веб-платформа)
	Администратор (для модерации и публикации)
	Нейросетевая модель синтеза речи
	База данных учебных материалов
Описание процесса:
1.	Преподаватель авторизуется в системе с правами преподавателя.
2.	Преподаватель переходит в раздел «Управление контентом» → «Создать модуль».
3.	Система отображает форму создания нового учебного модуля.
4.	Преподаватель заполняет основную информацию о модуле:
	Название модуля
	Описание
	Уровень сложности (начальный, средний, продвинутый)
	Тематическая категория
	Целевые компетенции
	Примерное время прохождения
5.	Преподаватель создает структуру модуля:
	Добавляет уроки в модуль
	Определяет последовательность уроков
	Устанавливает зависимости между уроками
6.	Для каждого урока преподаватель: a. Добавляет теоретический материал:
	Текстовый контент на коми и русском языках
	Грамматические правила
	Примеры использования b. Добавляет словарный запас:
	Новые слова и фразы
	Перевод
	Примеры предложений
	Аудио произношение (или генерация через TTS) c. Создает интерактивные упражнения:
	Выбирает тип упражнения (перевод, сопоставление, заполнение пропусков, аудио-распознавание)
	Формулирует задания
	Указывает правильные ответы
	Настраивает систему оценки
	Добавляет подсказки d. Добавляет мультимедийный контент:
	Изображения
	Аудиозаписи
	Видео материалы (если есть)
7.	Преподаватель настраивает параметры урока:
	Проходной балл
	Количество попыток
	Время на выполнение (если ограничено)
	Условия открытия следующего урока
8.	Преподаватель добавляет диалоговые сценарии (опционально):
	Создает структуру диалога
	Добавляет реплики на коми языке
	Указывает возможные варианты ответов ученика
	Настраивает критерии оценки ответов
	Определяет ветвления диалога
9.	Преподаватель сохраняет модуль как черновик.
10.	Система выполняет автоматическую проверку:
	Проверка наличия всех обязательных полей
	Проверка корректности ссылок на аудио
	Проверка наличия правильных ответов для всех упражнений
	Генерация аудио через TTS для новых слов
	Проверка орфографии и грамматики
11.	При наличии ошибок система сообщает преподавателю для исправления.
12.	После устранения ошибок преподаватель отправляет модуль на модерацию.
13.	Администратор получает уведомление о новом модуле на модерации.
14.	Администратор проверяет модуль:
	Качество контента
	Методическую правильность
	Соответствие уровню сложности
	Корректность переводов
	Качество аудио
	Работоспособность упражнений
15.	Администратор может:
	Одобрить модуль для публикации
	Отправить на доработку с комментариями
	Внести правки самостоятельно (с уведомлением преподавателя)
16.	При одобрении администратор:
	Устанавливает дату публикации
	Определяет целевую аудиторию
	Добавляет модуль в каталог доступных
17.	Система публикует модуль и делает его доступным для учеников.
18.	Система уведомляет преподавателя о публикации.
19.	Преподаватель может отслеживать статистику использования модуля:
	Количество прохождений
	Средние результаты
	Часто допускаемые ошибки
	Отзывы учеников

Выбор и обоснование стека технологий для веб-приложения «Коми кыв»
Выполнил: Тараканов В. В. Группа 335А
1. Что требуется от стека
	Прежде чем сравнивать технологии, надо разобраться, что именно система будет делать. Во-первых, это тесная интеграция с нейросетями: распознавание речи ученика (ASR), синтез речи на коми языке (TTS) и генерация контекстных ответов (NLP). Во-вторых, это работа с долгими задачами: генерация аудио и анализ произношения занимают от 2 до 10 секунд, поэтому система не может просто «ждать» ответа в синхронном HTTP-запросе – нужны очереди и фоновые воркеры. В-третьих, это классическая многопользовательская платформа с тремя ролями (Ученик, Преподаватель, Администратор), конструктором учебных модулей и системой геймификации. 
Из нефункциональных требований критически важны: безопасность (голосовые слепки – это биометрия, требуется соблюдение 152-ФЗ), отказоустойчивость (ТЗ прямо требует «деградированного режима» при падении ML-сервисов) и асинхронность. На прохождение практики отведено 8 недель, поэтому стек должен позволять быстро прототипировать REST API, но при этом легко масштабироваться до микросервисов.
2. Кандидаты
Для сравнения я взял три связки, на которых сегодня строят образовательные платформы с элементами ИИ и сложной бизнес-логикой:
	Вариант А – Python + FastAPI, БД PostgreSQL, отдельный фронтенд на React + TypeScript, Celery + Redis для очередей, Docker для контейнеризации ML-моделей.
	Вариант Б – Python + Django (и Django REST Framework), БД PostgreSQL, React + TypeScript, Celery + Redis.
	Вариант В – Node.js + NestJS, БД PostgreSQL, React + TypeScript, BullMQ + Redis.
Сразу можно сказать, что варианты вроде PHP (Laravel) или Go не подходят. PHP имеет слабую экосистему для машинного обучения (придётся поднимать отдельные Python-сервисы и настраивать сложный gRPC/HTTP обмен), а Go обладает слишком высоким порогом входа для учебного проекта, где нужно сосредоточиться на бизнес-логике и ML, а не на борьбе с типизацией и указателями.
3. Методика оценки
Использован метод экспертных оценок в виде взвешенной суммы критериев. Роль «экспертов» здесь играют опубликованные данные и мнения десятков тысяч практикующих разработчиков: ежегодный опрос Stack Overflow Developer Survey 2025 [1], отчёт JetBrains Python Developers Survey 2025 [2], рейтинг СУБД DB-Engines [3], официальная документация фреймворков [4, 5] и технические разборы на Хабре [6, 7].

Важность задаётся весом: 1 – низкая, 2 – средняя, 3 – критическая. Итог по стеку – сумма произведений «балл × вес»; максимум при сумме весов 30 составляет 300 баллов.

4. Разбор по группам критериев
Технологическая зрелость (K1–K3). Django развивается под управлением Django Software Foundation с предсказуемыми LTS-релизами (Б – 10). FastAPI развивается быстрее, релизы выходят чаще, но обратная совместимость соблюдается строго (А – 9). У NestJS (В – 8) экосистема Node.js меняется очень быстро, что требует частого обновления зависимостей. Сообщество и документация великолепны у всех трёх вариантов, но у Python-стеков (А, Б) она лучше структурирована для задач Data Science и ML (K2: А – 9, Б – 10, В – 8). По рынку труда Python и JavaScript делят первые строчки опросов [1] (K3: А – 9, Б – 9, В – 9).
Производительность и масштабируемость (K4–K6). Главный аргумент за Django – комплект «из коробки»: ORM с миграциями, аутентификация и готовая админ-панель, которая идеально закрывает задачи модератора и конструктора модулей из ТЗ [7] (Б – 10). В FastAPI админки нет, придётся использовать сторонние библиотеки вроде sqladmin или писать интерфейсы на React (А – 8). В Node.js (В – 7) админку тоже нужно собирать с нуля. 
Однако по асинхронности (K5) безоговорочный лидер – FastAPI. ТЗ требует обработки аудио-потоков и генерации звука. FastAPI нативно поддерживает asyncio и WebSockets. Django исторически синхронна, и для неблокирующего I/O придётся подключать Django Channels и ASGI-серверы, что утяжеляет архитектуру (Б – 6). Node.js имеет событийную модель, но проигрывает в связке с ML (В – 8). Вес K6 низкий, так как на одном VPS разницу увидеть негде.
Соответствие предметной области (K7–K9). По интеграции с ML (K7) разрыв самый заметный. Ядро системы – модели Whisper (ASR), Silero (TTS) и NLP-агенты. Все они написаны на Python и используют PyTorch/HuggingFace. В FastAPI и Django их можно импортировать и запускать в отдельных контейнерах, общаясь через очереди (А – 10, Б – 9). В Node.js (В – 4) придётся поднимать отдельные Python-микросервисы и настраивать между ними gRPC или HTTP-взаимодействие, что добавит задержку (latency) и усложнит отладку. 
Важное техническое уточнение: локальные ML-модели потребляют много CPU/GPU. Если запустить их напрямую в асинхронном event loop FastAPI, они заблокируют поток (из-за GIL и тяжёлых вычислений), и сервер перестанет отвечать другим клиентам. Поэтому, согласно ТЗ (раздел 4.1.1), ML-задачи обязательно нужно выносить в отдельные контейнеры-воркеры и использовать очереди (Celery + Redis) [6]. FastAPI в связке с Celery справляется с этим элегантнее, чем монолитная Django (K8: А – 9, Б – 9, В – 8). Поддержка SPA (K9) у всех на высоте, так как фронтенд отделён.
Безопасность и надёжность (K10–K11). Django строилась по принципу «security-first»: защита от CSRF, XSS и SQL-инъекций включена по умолчанию, что критично для соблюдения 152-ФЗ при работе с биометрией (Б – 10). В FastAPI (А – 8) это нужно настраивать вручную, но библиотека pydantic даёт строжайшую валидацию входных данных, а для шифрования голосовых слепков перед сохранением в БД отлично подходит cryptography. 
По отказоустойчивости (K11) FastAPI выигрывает. ТЗ требует, чтобы при падении ML-сервисов система переходила в «деградированный режим» (доступны только текстовые упражнения). Микросервисную архитектуру на FastAPI построить проще: если ML-контейнер упадёт, FastAPI-шлюз просто вернёт fallback-ответ. Django – это монолит, и выделить из неё ML-сервисы без переписывания архитектуры сложнее (А – 10, Б – 7, В – 8).
Экономические факторы и документация (K12–K15). Все стеки – свободное ПО (K12: А – 9, Б – 9, В – 9). Стоимость разработки (K13) определяется навыками. Python – основной язык на кафедре ИСиТ, поэтому А и Б получают по 9 баллов. JavaScript (В – 6) потребует переключения контекста и изучения новых паттернов ООП в TypeScript. Русскоязычной документации по FastAPI и Django в рунете предостаточно [6, 7] (K14: А – 8, Б – 9, В – 7).
Слабые места выбранного варианта. FastAPI критикуют за отсутствие встроенной админ-панели и ORM (он полагается на SQLAlchemy или Tortoise ORM) [6, 7]. Для «Дневника синоптика» это было бы фатально, но в «Коми кыв» основная сложность – это ML-пайплайны и асинхронные очереди, а админку для модерации контента можно быстро реализовать на React или подключить sqladmin.

Отчет о дополнительных инструментах разработки

Выполнил: Тараканов Владислав группа 335А

В частности, требовалось реализовать наглядный аудио-интерфейс для тренировки произношения, создать производительный конструктор учебных модулей и обеспечить администратора инструментами модерации контента. 
Ниже представлено подробное описание трех дополнительных инструментов, которые я выбрал.
1.	WaveSurfer.js
1.1. Название и Тип
WaveSurfer.js. Тип: Библиотека JavaScript / Интерактивный UI-виджет для визуализации и управления аудио. Разработчик: Open-source сообщество (Katspaugh).
1.2. Цель и Функциональность
	Главная задача: Предоставление удобного API для визуализации аудиодорожек (отрисовка волновой формы — waveform) и управления воспроизведением/записью с использованием Web Audio API и HTML5 Canvas.
	Ключевые возможности: Отрисовка звуковой волны в реальном времени, управление воспроизведением, интеграция с микрофоном для записи голоса (через официальный плагин RecordPlugin), выделение временных интервалов на дорожке (Regions) для фокусировки на отдельных словах.
	Преимущества: Высокая производительность при работе с тяжелыми аудиофайлами, легковесность, кроссплатформенность и отличная адаптация под компонентный подход React.
1.3. Контекст Применения в Проекте
	Где использована: В бизнес-процессах «Тренировка диалога с нейросетью» и «Прохождение интерактивного урока» (модуль ASR-анализа произношения).
	Решаемые задачи: Визуализация эталонного произношения (сгенерированного TTS-моделью Silero) и записанного ответа ученика. Ученик может визуально сравнить свою интонацию, паузы и громкость с эталоном. Также библиотека используется для записи голоса с микрофона и последующей отправки Blob-объекта на бэкенд для распознавания (ASR).
	Обоснование выбора: Стандартный HTML5 тег <audio> не предоставляет визуализации звуковой волны, что критически важно для обучения фонетике и интонации. WaveSurfer.js идеально закрывает потребность в наглядном аудио-интерфейсе и поддерживает запись с микрофона без необходимости писать сложный низкоуровневый код на Web Audio API.
1.4. Пример Реализации
import { useEffect, useRef } from 'react';
import WaveSurfer from 'wavesurfer.js';
import RecordPlugin from 'wavesurfer.js/dist/plugins/record';
const AudioRecorder = ({ onRecordingComplete }) => {
const containerRef = useRef(null);
const wavesurferRef = useRef(null);
const recordRef = useRef(null);
useEffect(() => {
// Инициализация WaveSurfer для отрисовки волны
wavesurferRef.current = WaveSurfer.create({
container: containerRef.current,
waveColor: '#4B8BBE', // Цвет волны (в стиле коми орнаментов)
progressColor: '#31527A',
height: 100,
});
// Подключение плагина записи с микрофона
recordRef.current = wavesurferRef.current.registerPlugin(RecordPlugin.create());
// Очистка памяти при размонтировании компонента (критично для Web Audio API)
return () => {
wavesurferRef.current?.destroy(); 
};
}, []);
const startRecording = () => recordRef.current?.startRecording();
const stopRecording = async () => {
await recordRef.current?.stopRecording();
const blob = recordRef.current?.getRecordedBlob();
// Отправка аудиофайла на FastAPI бэкенд для анализа ASR-моделью Whisper
if (blob) onRecordingComplete(blob); 
};
return (
<div>
<div ref={containerRef} />
<button onClick={startRecording}>Начать запись</button>
<button onClick={stopRecording}>Завершить и отправить на проверку</button>
</div>
);
};
Пояснение: Данный компонент решает задачу записи ответа ученика на коми языке. Использование useRef предотвращает лишние перерисовки React-компонента при обновлении аудио-потока. Метод destroy() в useEffect решает проблему утечек памяти и "зависания" микрофона при переходе между упражнениями.
1.5. Влияние и Результат
	Влияние на разработку: Значительно ускорило создание модуля записи и анализа произношения. Мне не пришлось самостоятельно писать алгоритмы отрисовки Canvas и работать с MediaRecorder API.
	Результат: Ученики получили наглядный инструмент для самокоррекции. Визуальное сравнение волн помогает понять, где ученик делает неправильные паузы или ударения.
	Сложности: Потребовалось внимательно следить за жизненным циклом компонента в React, чтобы корректно освобождать ресурсы Web Audio API, иначе браузер блокировал доступ к микрофону после 3-4 записей.
1.6. Альтернативы
	Howler.js: Отличная библиотека для воспроизведения, но в ней нет встроенной продвинутой визуализации волны и записи с микрофона из коробки.
	Tone.js: Ориентирована на синтез музыки и сложные аудио-эффекты. Избыточна и слишком сложна для базовой записи голоса и отрисовки волны.
 
2.	React Hook Form
2.1. Название и Тип
React Hook Form. Тип: Библиотека JavaScript для управления формами в экосистеме React. Разработчик: Beier (Bluebill1049).
2.2. Цель и Функциональность
	Главная задача: Управление состоянием форм и их валидацией в React-приложениях с минимальным количеством перерисовок (re-renders), используя неконтролируемые компоненты и useRef.
	Ключевые возможности: Регистрация полей, интеграция со схемами валидации (Zod/Yup), управление ошибками, работа с глубоко вложенными объектами и динамическими массивами через useFieldArray.
	Преимущества: Высокая производительность (форма не перерисовывается при каждом нажатии клавиши), малый размер бандла, отличный Developer Experience (DX).
2.3. Контекст Применения в Проекте
	Где использована: В бизнес-процессе «Добавление нового учебного модуля» (Конструктор учебных модулей для Преподавателя).
	Решаемые задачи: Создание сложных, многошаговых форм с динамическим добавлением уроков, словарных слов, интерактивных упражнений и диалоговых сценариев.
	Обоснование выбора: Конструктор модулей требует работы с глубоко вложенными JSON-структурами (Модуль -> Уроки -> Упражнения -> Варианты ответов). Использование стандартного useState вызвало бы огромное количество перерисовок и "лаги" при вводе текста. React Hook Form идеально справляется с объемными формами, обеспечивая плавный UX для преподавателей.
2.4. Пример Реализации
import { useForm, useFieldArray } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { moduleSchema } from './validationSchemas'; // Схема Zod для валидации

const ModuleConstructor = () => {
const { register, control, handleSubmit, formState: { errors } } = useForm({
resolver: zodResolver(moduleSchema),
defaultValues: {
title: '',
vocabulary: [{ word: '', translation: '' }],
},
});
// Использование useFieldArray для динамического списка слов
const { fields, append, remove } = useFieldArray({
control,
name: 'vocabulary',
});
const onSubmit = (data) => {
// Отправка сложного JSON-объекта на эндпоинт FastAPI
console.log('Отправка черновика на бэкенд:', data); 
};
return (
<form onSubmit={handleSubmit(onSubmit)}>
<input {...register('title')} placeholder="Название модуля" />
{errors.title && <span className="error">{errors.title.message}</span>}
<h3>Словарь урока</h3>
{fields.map((field, index) => (
<div key={field.id} className="vocab-row">
<input {...register(`vocabulary.${index}.word`)} placeholder="Слово на коми" />
<input {...register(`vocabulary.${index}.translation`)} placeholder="Перевод" />
<button type="button" onClick={() => remove(index)}>Удалить</button>
</div>
))}
<button type="button" onClick={() => append({ word: '', translation: '' })}>
Добавить слово
</button>
<button type="submit">Сохранить черновик</button>
</form>
);
};
Пояснение: Код демонстрирует создание динамического списка словарных слов. Метод useFieldArray берет на себя всю логику добавления и удаления строк, сохраняя корректные индексы для последующей сериализации в JSON. Интеграция с zodResolver гарантирует, что на бэкенд (в Pydantic-модели FastAPI) уйдут только валидные данные.
2.5. Влияние и Результат
	Влияние на разработку: Сэкономило мне десятки часов на написание кастомных редьюсеров и обработчиков событий для каждого поля ввода.
	Результат: Преподаватели могут быстро и без зависаний интерфейса наполнять модули контентом. Валидация на клиенте работает синхронно с Pydantic-схемами на сервере.
	Сложности: При интеграции с некоторыми сторонними UI-библиотеками (например, кастомными выпадающими списками или редакторами текста) приходилось использовать компонент <Controller />, что слегка усложняло верстку.
2.6. Альтернативы
	Formik: Очень популярна, но вызывает re-render всей формы при каждом нажатии клавиши, что недопустимо для конструктора на 50+ полей (интерфейс начинает "тормозить").
	Redux Form: Устарела, тяжелая, избыточна для локального состояния форм, не подходит для современного React-стека.
 
3.	SQLAdmin
3.1. Название и Тип
SQLAdmin. Тип: Плагин / Библиотека Python для FastAPI и Starlette. Разработчик: Amir S. (aminalaee).
3.2. Цель и Функциональность
	Главная задача: Быстрое создание полнофункциональных административных панелей (CRUD-интерфейсов) для приложений на базе FastAPI и SQLAlchemy.
	Ключевые возможности: Автоматическая генерация таблиц с данными, пагинация, фильтрация, поиск, кастомизация действий (кнопок) и интеграция с асинхронными сессиями БД.
	Преимущества: Нативная поддержка asyncio, легкий вес, отсутствие необходимости поднимать отдельный фронтенд-проект для базовых админских задач.
3.3. Контекст Применения в Проекте
	Где использована: В подсистеме администрирования (роль «Администратор») для модерации пользовательского и преподавательского контента.
	Решаемые задачи: Просмотр черновиков учебных модулей, управление ролями пользователей, просмотр логов ошибок ML-сервисов, управление базовым словарным запасом.
	Обоснование выбора: В отчете «Выбор и обоснование стека технологий» я отмечал главный минус FastAPI — отсутствие встроенной админки (в отличие от Django). Писать полноценный SPA-интерфейс для админки с нуля на React было бы слишком затратно по времени (на практику отведено 8 недель). SQLAdmin позволил мне за пару дней закрыть все потребности Администратора, подключившись напрямую к моделям SQLAlchemy.
3.4. Пример Реализации
from sqladmin import Admin, ModelView
from fastapi import FastAPI
from models import User, Module
from db import async_session_maker
from services.tts_service import trigger_tts_generation
app = FastAPI(title="Коми кыв API")
admin = Admin(app, async_session_maker)
class UserAdmin(ModelView, model=User):
column_list = [User.id, User.email, User.role, User.is_active]
column_searchable_list = [User.email]
can_edit = True
can_delete = False # Запрещаем физическое удаление (152-ФЗ), только деактивация

class ModuleAdmin(ModelView, model=Module):
column_list = [Module.id, Module.title, Module.status, Module.author_id]
column_filters = [Module.status] # Фильтр по статусу модерации
async def on_model_change(self, data, model, is_created):
# Кастомная логика: при одобрении модуля триггерим генерацию TTS в Celery
if data.get("status") == "published" and model.status != "published":
await trigger_tts_generation(model.id)
await super().on_model_change(data, model, is_created)
admin.add_view(UserAdmin)
admin.add_view(ModuleAdmin)
Пояснение: В данном фрагменте я настроил представление для модели Module. Переопределение метода on_model_change решает важную бизнес-задачу: как только Администратор меняет статус модуля на "Опубликован", система автоматически ставит задачу в очередь Celery для генерации аудиофайлов (TTS) через модель Silero.
3.5. Влияние и Результат
	Влияние на разработку: Сэкономило мне десятки часов разработки фронтенда и верстки таблиц для внутренних нужд.
	Результат: Администратор получил удобный, безопасный и адаптивный интерфейс для модерации контента и управления БД, который работает поверх основного API.
	Сложности: Ограниченные возможности по кастомизации сложной бизнес-логики прямо в шаблонах интерфейса. Для специфических действий (например, "Отправить на доработку с комментарием") мне пришлось писать кастомные эндпоинты в FastAPI и делать AJAX-запросы из админки.
3.6. Альтернативы
	Написание кастомной админки на React: Долгое время разработки, избыточно для внутреннего инструмента, который нужен только 1-2 администраторам.
	FastAPI-Admin: Менее зрелая экосистема, хуже поддержка асинхронного SQLAlchemy 2.0 и меньше готовых виджетов для фильтров.
